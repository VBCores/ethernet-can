# Project Summary

This repository contains the Linux host bridge for VBCores Ethernet-CAN boards. The host process translates between Ethernet-CAN UDP packets and Linux SocketCAN interfaces. It supports multiple Ethernet-CAN boards behind one shared host IP; boards are distinguished by UDP source IP, and each board maps its logical buses `0..5` to configured Linux VCAN interfaces.

## Important Files

- `src/main.cpp`: Main host bridge. This is the runtime binary built by CMake. It owns UDP, SocketCAN sockets, epoll, per-board runtime state, packet parsing, and CAN frame forwarding.
- `extra/start_ethernet_can.py`: Launcher and host state sync. It scans host `.json` configs, validates them, creates/configures required `vcan` interfaces, and starts the host binary with generated CLI arguments.
- `extra/configs/example.json`: Host-side board config template. Each `.json` describes one board.
- `extra/SD-card/config.json`: SD-card config template for firmware identity overrides, explicit static/P2P network settings, and locked board-managed runtime fields.
- `extra/ethernet-can.service`: systemd unit that runs the Python launcher.
- `extra/10-ethernet-can.yaml`: netplan example for simple point-to-point host networking.
- `instructions/multiple_boards_web_config/README.md`: Practical guide for connecting two boards to one host.
- `README.md`: User-facing setup guide. Keep it aligned with launcher/config behavior when those change.
- `CMakeLists.txt`: Builds `src/*.cpp` into `ethernet-can` and installs the binary, launcher, and service file.

## Runtime Model

The host binary does not parse JSON files. It expects explicit CLI arguments generated by the launcher:

```bash
ethernet-can \
  --host-ip 192.168.0.100 \
  --board board1 --device-ip 192.168.0.2 --period 10000000 --bus0 vcan1.0 \
  --board board2 --device-ip 192.168.0.3 --period 10000000 --bus0 vcan2.0
```

`extra/start_ethernet_can.py` sends board runtime config to each board over HTTP REST before launching the host binary only when host JSON contains `fdcan`. Without `fdcan`, it waits for a board-applied runtime config and takes the period from the board. While the host binary runs, the launcher polls `GET /api/v1/status`; host-managed boards are reconfigured after repeated no-response or config mismatch failures. `src/main.cpp` binds one UDP socket to `--host-ip:1556` for CAN data only. Incoming UDP datagrams are dispatched by source IP to the correct board session. Literal IPv4 `--device-ip` values are used directly. Hostnames are resolved at startup and re-resolved when UDP arrives from an unknown source.

CAN bus IDs in packets remain logical bus numbers `0..5`. The host maps those logical buses to Linux interface names from the config.

## Packet Format

The host preserves the existing firmware wire format:

- UDP server port on host: `1556`
- UDP client port on board: `1555`
- Runtime config is applied over HTTP `PUT /api/v1/config`; UDP startup config is deprecated and must not be sent by the host binary.
- CAN frame packet records use 1 byte length, 4 bytes encoded bus/CAN ID, then payload
- Encoded bus/CAN ID uses top 3 bits for bus number and lower 29 bits for extended CAN ID
- H7 may send a 4-byte UDP heartbeat packet `EHB1`; host code treats it as service traffic and never forwards it to SocketCAN.

If frames arrive from the board but are not visible in `candump`, inspect:

- Launcher `Launching:` line: confirm expected `--busN iface` args are present.
- The relevant `network.host_interface_map` entry: bus presence is what enables forwarding.
- `candump` interface: it must match the mapped interface, for example `vcan2.0`.
- Source IP: incoming UDP source should match the current resolved `Device_IP_address`; for hostnames, unknown sources trigger a re-resolve.

## Build notes

This project is currently Linux-native. `src/main.cpp` uses SocketCAN, epoll, and timerfd.

## Exploration Guide

Start with `README.md` for the user-facing flow, then read `extra/configs/example.json` and `extra/start_ethernet_can.py` to understand how configs become CLI arguments. Read `src/main.cpp` after that; its main control flow is:

1. Parse CLI into `BoardConfig` records.
2. Construct `HostBridgeApp`.
3. Open one UDP socket and per-board CAN sockets.
4. Register UDP, CAN, and timer fds in epoll.
5. Dispatch events in the main loop.

The two central C++ classes are:

- `BoardSession`: owns one board's CAN sockets, timer, UDP target address, and transmit bundle.
- `HostBridgeApp`: owns the shared UDP socket, epoll loop, board lookup by source IP, and fd-to-event binding table.
